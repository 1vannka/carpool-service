# Корпоративный веб-сервис совместных поездок (Carpooling)

## Цель проекта
Разработать изолированную платформу для организации совместных поездок сотрудников компании (карпулинг). Система позволяет водителям создавать маршруты, а пассажирам находить подходящие машины "по пути" с помощью умного гео-мэтчинга или ручного поиска.

---

## Архитектура и Компоненты

Система спроектирована как **модульный монолит** с четким разделением слоев (Clean Architecture). Логика изолирована в рамках одной компании, но имеет возможность быть расширенной.

### 1. Бэкенд (Java Spring Boot)
Ядро системы, реализующее порты и адаптеры для сохранения независимости домена от внешних зависимостей.
* **Стиль:** Controller - Service - Repository.
* **Гео-поиск:** Интеграция с JTS (Java Topology Suite) и Hibernate Spatial. Поиск пересечений маршрутов на уровне нативных SQL-запросов (PostGIS `ST_DWithin`).
* **Уведомления:** Асинхронный пуш через Server-Sent Events (SSE). Состояние коннектов хранится в RAM (stateful).
* **Конкурентность:** Защита от овербукинга мест в машине реализована через Optimistic Locking (`@Version`).

### 2. База данных (PostgreSQL + PostGIS)
Единая точка хранения состояния. 
* Все пространственные данные лежат в системе координат WGS 84 (SRID 4326).
* Для поиска используются индексы `GIST` по координатам и геометрии маршрутов.
* Самоочистка старых поездок и заявок выполняется фоновыми `@Scheduled` задачами.

### 3. Фронтенд (Vue 3)
Клиентская часть для сотрудников и администраторов.
* **Карты:** Leaflet + OpenStreetMap.
* **Маршрутизация:** Интеграция с OpenRouteService (ORS) для построения полилиний графов на стороне клиента (до отправки на сервер).
* **UI:** Скелет построен на PrimeVue и Tailwind CSS.

---

## Технический стек

* **Бэкенд:** Java, Spring Boot (Web, Security, Data JPA).
* **Базы данных:** PostgreSQL (PostGIS), Redis (только для хранения refresh-токенов).
* **Фронтенд:** Vue 3 (Composition API), TypeScript, Vite.
* **Гео-стек:** OpenRouteService API, JTS, Leaflet.
* **Документация API:** Springdoc-openapi (Swagger UI).

## Схема и сущности базы данных (PostgreSQL + PostGIS)

Все пространственные данные хранятся и обрабатываются в системе координат WGS 84 (SRID 4326). Для оптимизации гео-запросов на критических полях используются пространственные индексы GIST.

* **users** (Сотрудники компании)
    * `id` (BIGSERIAL, PK) - уникальный идентификатор.
    * `email` (VARCHAR, Unique) - корпоративная почта (с валидацией домена).
    * `password_hash` (VARCHAR) - хэш пароля.
    * `first_name`, `last_name` (VARCHAR) - имя и фамилия.
    * `telegram_alias`, `vk_alias` (VARCHAR, Nullable) - контакты для связи.
    * `role` (VARCHAR) - роль в системе (USER, ADMIN).

* **offices** (Офисы компании)
    * `id` (BIGSERIAL, PK) - уникальный идентификатор.
    * `name`, `city`, `address` (VARCHAR) - информация о филиале.
    * `location` (Geometry Point, SRID 4326) - географическая точка офиса.
    * *Индексы:* GIST на поле `location`.

* **trips** (Созданные поездки водителей)
    * `id` (BIGSERIAL, PK) - уникальный идентификатор поездки.
    * `driver_id` (BIGINT, FK -> users) - водитель (связь один-ко-многим, каскадное удаление).
    * `office_id` (BIGINT, FK -> offices) - целевой офис назначения (каскадное удаление).
    * `departure_time` (TIMESTAMPTZ) - время выезда.
    * `estimated_duration` (INTEGER) - расчетная длительность в минутах.
    * `total_seats`, `available_seats` (INTEGER) - общее и свободное количество мест.
    * `car_model`, `car_color`, `car_plate` (VARCHAR) - данные автомобиля.
    * `route_path` (Geometry LineString, SRID 4326) - геометрия маршрута поездки.
    * `start_location` (Geometry Point, SRID 4326) - начальная точка маршрута.
    * `version` (BIGINT) - поле для оптимистической блокировки (защита от овербукинга).
    * `status` (VARCHAR) - статус поездки (CREATED, IN_PROGRESS, COMPLETED, CANCELED).
    * *Индексы:* GIST на поле `route_path`.

* **trip_passengers** (Связующая таблица поездок и пассажиров)
    * `trip_id` (BIGINT, FK -> trips) - идентификатор поездки.
    * `passenger_id` (BIGINT, FK -> users) - идентификатор пассажира.
    * `status` (VARCHAR) - статус заявки (WAITING_APPROVAL, CONFIRMED).
    * *Ключи:* Составной PK (trip_id, passenger_id). Каскадное удаление при очистке связанных сущностей.

* **ride_requests** (Заявки пассажиров на поиск машины)
    * `id` (BIGSERIAL, PK) - уникальный идентификатор заявки.
    * `passenger_id` (BIGINT, FK -> users) - создатель заявки (каскадное удаление).
    * `office_id` (BIGINT, FK -> offices) - целевой офис (каскадное удаление).
    * `pickup_location` (Geometry Point, SRID 4326) - точка, откуда нужно забрать пассажира.
    * `target_time` (TIMESTAMPTZ) - желаемое время прибытия.
    * `tolerance_time` (INTEGER) - допустимое окно отклонения во времени (в минутах).
    * `status` (VARCHAR) - статус запроса (PENDING, EXPIRED).
    * *Индексы:* GIST на поле `pickup_location`.

## API Эндпоинты

Документация доступна в Swagger UI (`/swagger-ui/index.html`) после запуска приложения. Основные контроллеры:

**Авторизация (JWT) `/api/auth`**
* `POST /register` - Регистрация (валидация корпоративного домена).
* `POST /login` - Вход (выдача access и refresh токенов).
* `POST /refresh` - Обновление токена.
* `POST /logout` - Выход.
* `POST /logout-all` - Инвалидация всех сессий (сброс в Redis).

**Профиль `/api/profile`**
* `GET /` - Получить текущий профиль.
* `PUT /` - Обновить данные (в т.ч. контакты Telegram/VK).

**Поездки водителя `/api/trips`**
* `POST /` - Создать поездку (парсинг LineString из массива координат).
* `GET /my-active` - Получить свою активную поездку.
* `PUT /{id}` - Обновить детали.
* `DELETE /{id}` - Отменить поездку.
* `GET /matching` - Умный поиск (гео-мэтчинг).
* `GET /` - Ручной поиск.

**Управление пассажирами `/api/trips/{tripId}`**
* `POST /join` - Подать заявку в чужую поездку.
* `GET /passengers` - Список пассажиров в машине.
* `GET /my-status` - Статус текущей заявки.
* `POST /passengers/{passengerId}/approve` - Одобрить попутчика.
* `DELETE /passengers/{passengerId}/reject` - Отклонить попутчика.
* `DELETE /passengers/my-request` - Отменить свою заявку.
* `POST /passengers/{passengerId}/ping` - Пуш-уведомление "Я подъезжаю".

**Заявки пассажиров `/api/ride-requests`**
* `POST /` - Создать заявку на поездку.
* `GET /my-active` - Текущая активная заявка.
* `DELETE /{id}` - Отменить заявку.

**Управление офисами `/api/offices` (Нужна роль ADMIN)**
* `GET /` - Список локаций.
* `POST /` - Добавить новый офис (координаты с карты).
* `PUT /{id}` - Обновить офис.
* `DELETE /{id}` - Удалить (ON DELETE CASCADE для связанных поездок).

**Уведомления (SSE) `/api/notifications`**
* `GET /subscribe` - Подключение к потоку пуш-уведомлений.

## Развертывание и Запуск (Docker)

В проекте предусмотрено два варианта развертывания.

### Вариант 1: Локальная разработка (ветка `master`)
В ветке `master` `docker-compose.yml` содержит только инфраструктурные зависимости (БД и кэш). Бэкенд и фронтенд запускаются локально через IDE/терминал.

### Вариант 2: Полная изоляция (ветка `devops`)
В ветке `devops` настроен full-stack контейнеризация. `docker-compose.yml` собирает и поднимает все сервисы разом: БД, Redis, Backend (Java) и Frontend (Vue) в отдельных контейнерах.

## Ключевые бизнес-сценарии

### 1. Защита от спама и лимиты на активность
Система исключает путаницу в координации: один пользователь может иметь только одну активную сущность в системе одновременно. Нельзя создать две поездки, две заявки на поездку или быть одновременно водителем и пассажиром в активных процессах. Чтобы запустить новый флоу, старый процесс нужно завершить или отменить.

### 2. Панель администратора (Управление офисами)
Сотрудники с ролью `ROLE_ADMIN` имеют доступ к закрытому разделу `/admin/offices`, где могут управлять точками назначения компании:
* **Просмотр:** Для админа реализован такой же выбор города и просмотр точек офисов, но добавляется специальная кнопка "Добавить офис".
* **Добавление:** Администратор может нажать на кнопку "Добавить офис" и в появившейся форме указать данные офиса, адрес указывается двумя способами:
    * Ввод конкретного адреса, точка с эти адресом отрисовывается на карте для проверки корректности.
    * Указание точки с использованием прицела прямо на карте.
* **Удаление:** Завязано на `ON DELETE CASCADE` в базе данных. Удаление офиса автоматически и безопасно подчищает все привязанные к нему поездки и заявки.

### 3. Режим наблюдателя (Просмотр до создания заявки/поездки)
* **Свободный просмотр:** Любой сотрудник, у которого еще нет активной поездки или заявки, может просто кликнуть на нужный офис на карте. Фронтенд подтянет список всех поездок в выбранный офис, также есть возможность в карточке поезки нажать на кнопку отрисовки маршрута. Это позволяет заранее оценить трафик в выбранный офис.

### 4. Сценарий пассажира: Создание заявки и поиск
* **Инициализация:** Пассажир выбирает офис назначения, желаемое время прибытия и окно допуска (`tolerance_time`). Точку посадки (`pickup_location`) можно задать двумя способами:
    * Ввести конкретный адрес текстом (точка отрисовывается на карте для визуальной проверки).
    * Указать место прицелом прямо на интерактивной карте.
* **Умная фильтрация (Гео-мэтчинг):** Как только заявка создается и появляется в БД со статусом `PENDING`, свободный просмотр отключается. Теперь пассажир видит только целевые маршруты - те, которые проходят не дальше 1.5 км от его точки посадки. Фильтрация работает на уровне базы данных через PostGIS-функцию `ST_DWithin`.
* **Ожидание и Пуши (SSE):** Поскольку SSE-соединение устанавливается глобально еще на этапе входа в приложение, дополнительных коннектов при поиске не создается. Если подходящих вариантов на карте пока нет, пассажир просто ждет. Как только кто-то из водителей создаст подходящий маршрут, бэкенд отправит уведомление в уже открытую трубу, и пассажиру моментально прилетит пуш.

### 5. Сценарий водителя: Создание поездки
* **Инициализация маршрута:** Водитель выбирает целевой офис и задает стартовую точку. Способы указания старта аналогичны пассажирским:
    * Текстовый ввод точного адреса.
    * Ручная установка точки прицелом на карте.
* **Детали и Построение:** Водитель указывает время выезда, количество мест и данные машины. Фронтенд обращается к OpenRouteService и отрисовывает превью маршрута на карте.
* **Публикация:** При подтверждении бэкенд сохраняет поездку и немедленно запускает гео-поиск ждущих пассажиров (`PENDING`), чьи точки лежат рядом с новым маршрутом. Найденным пассажирам моментально рассылаются пуши через SSE.

### 6. Флоу согласования и динамический роутинг
1. **Запрос:** Пассажир (через пуш или из отфильтрованного списка) видит маршрут водителя и жмет "Присоединиться". Статус его заявки меняется на `WAITING_APPROVAL`.
2. **Пре-алерт водителю:** Водитель получает уведомление о запросе. На его карте поверх основного маршрута появляется временный желтый маркер точки посадки пассажира, чтобы водитель мог визуально оценить потенциальный крюк.
3. **Решение водителя и Перестроение трека:**
    * **Апрув:** Водитель одобряет заявку (транзакция защищена от гонки за место через `@Version`). Доступные места списываются, статус пассажира - `CONFIRMED`. Фронтенд водителя делает новый запрос к ORS, и маршрут на карте динамически перестраивается, чтобы проходить через точку нового попутчика. Желтый маркер зеленеет.
    * **Отказ:** Водитель жмет крестик. Запись `WAITING_APPROVAL` удаляется, маркер стирается с карты водителя. Пассажир откатывается в `PENDING` и ищет дальше.
4. **Отмена и Перерасчет:** Если пассажир отменяет свою заявку или выходит из поездки, связь в базе разрывается. Маршрут на карте водителя автоматически пересчитывается без учета точки выбывшего участника.
5. **Оффлайн-контакт и Навигация:** В карточке поездки у обоих участников появляется прямая ссылка на указанные контакты пассажира/водителя.
6. **Уведомление о приближении:** Подъезжая к пассажиру, водитель имеет возможность нажать на кнопку пинга в интерфейсе. Бэкенд отправляет конкретному пассажиру адресный SSE-пуш о том что водитель подъезжает к его точке.
